# 产品瘦身与整合改造设计

## 背景

当前仓库已经暴露出明显问题：

- 产品能力边界不清
- 同类功能入口分散
- 管理端页面多但稳定性不足
- 移动端是 WebView 壳，继承了 Web 端复杂导航和布局问题
- 音视频更像插件式会议，而不是成熟 IM 的直达通话
- 仓库内存在过多阶段性文档、审计文件、说明文件，影响主干可读性

这说明当前项目最需要的不是继续叠加功能，而是：

- 删减
- 收口
- 合并
- 建立清晰主路径

## 改造目标

本轮改造只追求三件事：

1. 让产品主路径更短
2. 让代码结构更清晰
3. 让仓库更干净、更适合持续开发

## 改造原则

### 1. 能删就删

满足以下任一条件的内容，优先删除：

- 只服务于一次性联调的临时文件
- 与主流程无关的备份/阶段总结/重复文档
- 代码路径上已经不再被引用的组件、工具、路由
- 多种实现并存但只有一种实际在走的旧实现

### 2. 能并就并

满足以下条件的内容，优先合并：

- 相邻但职责重叠的后台页面
- 同类系统诊断能力分散在多个低频页面
- 对用户来说难以区分的“好友 / 私信 / 会话”入口
- 同一类配置项分散在多个页面和文件里

### 3. 能短就短

满足以下条件的代码，优先缩短：

- 过长但职责单一的页面组件
- 重复的错误处理和状态判断
- 重复的 broker 调用包装
- 结构上可以通过公共 helper / hook / schema 收敛的逻辑

### 4. 先产品成立，再做包装

优先级固定：

1. 产品成立线
2. 后台运营线
3. 财讯包装线

不再反过来做。

## 范围拆分

### 第一阶段：仓库瘦身

目标：

- 清理无关文件
- 收紧文档入口
- 删除不再服务主流程的阶段性噪音

动作：

- 清理仓库根目录下散落的阶段性总结和中间文件
- 收敛文档入口到：
  - `README.md`
  - `CHANGELOG.md`
  - `docs/deployment/`
  - `docs/usage/`
  - `docs/superpowers/specs/`
- 删除明显重复或不再需要的说明文件

### 第二阶段：信息架构整合

目标：

- 缩短用户找消息、找好友、找群组的路径
- 减少“会话 / 好友 / 个人页 / 插件页”之间的认知跳转

动作：

- 重构个人侧边栏，把“好友”和“私信”收口成更明确的会话主路径
- 重新评估群聊、私聊、好友管理的导航层级
- 优先让“找消息”这件事一步可达

### 第三阶段：管理端收口

目标：

- 从“页面很多”变成“页面少但稳”

动作：

- 合并低频、强依赖、容易 500/503 的系统诊断页面
- 把 `network` / `socketio` / `cache` / `analytics` / `ops` 重新分层：
  - 核心运营页
  - 高级诊断页
- 对依赖 executor、broker、db 的页面统一做能力探测与降级

### 第四阶段：通话能力重定义

目标：

- 明确当前通话能力是“会议插件”，不是“好友直达语音”

动作：

- 先把现有 LiveKit 路线收口成可理解的“会议能力”
- 把“好友语音”从“像房间 / 像外链”的交互里分离出来
- 若当前底座不适合做真正直达语音，则在架构报告里明确止损建议

### 第五阶段：财讯包装

目标：

- 在产品主路径成立后再做高感知升级

动作：

- 登录页视觉升级
- 管理端视觉统一
- 群公告模板化
- 合规文案与品牌内容收口

## 删除策略

本轮允许删除：

- 仓库根目录无关阶段性总结文件
- 明显重复的部署说明
- 不再使用的临时脚本
- 未被引用的旧组件和旧路由

本轮不直接删除：

- 核心服务代码
- 当前生产部署链路文件
- 当前仍被路由引用的页面
- 可能被插件动态引用的核心注册文件

## 整合策略

### 管理端

建议目标：

- 登录后默认只保留少量高价值入口
- 高级诊断能力收进单独区域
- 不再把大量“系统内部结构视图”直接暴露为一线运营页面

### 客户端

建议目标：

- 私信、好友、会话统一理解
- 群组入口与消息入口收敛
- 先解决“怎么找到消息”，再谈复杂功能

### 移动端

建议目标：

- 先针对 WebView 场景做消息区、侧边栏、导航适配
- 不假装它是原生 IM
- 必要时明确哪些能力暂不承诺移动端体验

## 交付顺序

我会按这个顺序执行：

1. 仓库瘦身与文档收口
2. 管理端页面与路由能力矩阵
3. 客户端消息入口整合
4. 移动端关键体验修补
5. 通话能力重定义
6. 财讯包装

## 风险说明

### 风险 1：删错低频但仍有用的路径

控制方式：

- 删除前先做引用检查
- 先删根目录噪音与明显重复项

### 风险 2：收口导航后影响老路径

控制方式：

- 保留过渡跳转
- 先做结构收口，再处理细节样式

### 风险 3：音视频能力重定义后暴露底座限制

控制方式：

- 如当前插件机制只适合会议，不适合点对点通话，就明确写进结论
- 不再伪装为已经具备成熟好友语音能力

## 当前建议

本轮改造应接受一个现实：

- 这是一次结构性收缩和重建
- 不是继续在原有松散结构上缝补

如果继续推进，就按本设计执行，不再以“保持现状兼容一切”为目标。
