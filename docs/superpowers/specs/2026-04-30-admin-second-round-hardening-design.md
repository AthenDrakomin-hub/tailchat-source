# 管理端第二轮加固设计

## 1. 背景

第一轮已经解决了以下高频痛点：

- “系统设置”命名与位置不当，已调整为“站点配置”
- 站点配置页在后端配置服务不可用时不再直接 500
- 系统控制台在执行器未配置时有明确降级态
- 防御控制系统在插件未接入时有明确降级态
- 缓存管理修复了前后端错误字段不一致问题

但管理端仍存在第二层问题：

1. 仍有若干页面属于“伪功能页”，名称像功能页面，实际只是说明页或只读页  
2. 多个页面和动作仍然直接 `Message.error(String(err))`，错误信息对管理员不友好  
3. 页面对“能力是否存在”缺少统一建模，导致每页各写一套，后续维护会继续散掉  
4. 插件注册表、Socket.IO 入口等页面的定位不清晰，继续误导使用者

本轮目标不是扩展后台能力，而是继续做“可用性与认知修复”。

## 2. 目标

第二轮实现以下目标：

- 给剩余高风险页面补统一“能力检测 + 降级展示”
- 修正“插件发布与权限”“Socket.IO 长链接”等名称和页面定位
- 引入统一错误文案格式，替代零散 `String(err)` 直出
- 尽量减少“点开后才发现根本不能用”的情况

## 3. 非目标

本轮明确不做：

- 不新接入真实 Socket.IO 后台
- 不实现真正的插件权限编辑器
- 不改造整个管理端框架
- 不解决 `tailchat-admin build` 的全部历史工作区类型问题
- 不重写用户/群组/消息/文件等资源页的数据层

## 4. 现状问题清单

### 4.1 插件页定位问题

当前页面名为“插件发布与权限”，但实际行为是：

- 直接读 `/registry-be.json`
- 失败时静默返回空数组
- 页面文案自己承认“如需修改权限请直接编辑文件或通过环境变量控制”

问题：

- 名称过强，暗示这是一个真正的“管理”页面
- 实际只是“插件注册表查看器”
- 文件缺失时没有明确降级提示

### 4.2 Socket.IO 页面定位问题

当前页面名为“Socket.IO 长链接”，但实际行为是：

- 只显示服务 URL 文案
- 引导用户去打开外部网站 `admin.socket.io`

问题：

- 看起来像“后台子系统”
- 实际只是“诊断/说明入口”
- 没有检测当前系统是否真的具备可用的 Socket.IO 诊断条件

### 4.3 错误展示问题

当前多处页面仍直接：

- `Message.error(String(err))`

问题：

- 对管理员不可读
- 没有错误类型
- 没有“是未配置、未安装、无权限还是网络失败”的区分
- 无法形成一致的排错经验

### 4.4 统一能力模型缺失

第一轮已经在少数页面引入降级态，但每页都是“自己判断、自己渲染、自己写文案”。

问题：

- 逻辑重复
- 文案风格不统一
- 后续新增页面时仍会继续走散

## 5. 方案选型

### 方案 A：继续逐页补洞

做法：

- 哪页报错修哪页
- 保持当前每页各自处理异常

优点：

- 改动最小

缺点：

- 会继续形成碎片化逻辑
- 第三轮、第四轮还会重复返工

### 方案 B：先抽统一能力检测层，再整体套用

做法：

- 引入统一 `feature availability` 模型
- 自定义页面全部先走能力判断，再决定显示业务内容或降级卡片

优点：

- 后续维护最稳

缺点：

- 第一版改动略大

### 方案 C：混合方案（推荐）

做法：

- 抽一个非常轻量的统一能力/错误展示层
- 优先覆盖第二轮最高价值页面
- 不大改现有框架，只做最小可复用封装

推荐原因：

- 既能继续止血
- 又不会为了“架构完美”把这轮改动做过重

## 6. 设计方案

### 6.1 引入统一能力状态模型

前端新增一个轻量工具层，用于描述页面依赖的能力状态。

统一数据结构：

```ts
type FeatureState = {
  available: boolean;
  reason?: string;
  level?: 'info' | 'warning' | 'error';
  actionHint?: string;
};
```

用途：

- 页面可以统一判断“可用/不可用”
- 不可用时显示同风格的降级卡片
- 不再让每个页面自己拼文案

### 6.2 新增统一降级卡片组件

新增一个共享 UI 组件，例如：

- `FeatureStatusCard`

职责：

- 显示能力名称
- 显示当前状态
- 显示错误/未配置原因
- 显示下一步修复建议

适用范围：

- 插件缺失
- 配置缺失
- 外部文件缺失
- 外部诊断入口不可用

### 6.3 插件页重命名与降级

调整方向：

- 菜单名从“插件发布与权限”改为“插件注册表”
- 页面说明改为“当前仅用于查看后端插件注册表，不提供在线修改”

页面行为：

- 若 `/registry-be.json` 存在且可读：正常展示
- 若不存在或读取失败：显示统一降级卡片
- 不再静默返回空数组伪装“没数据”

预期收益：

- 用户不会再误以为这里可以在线发布插件或修改权限

### 6.4 Socket.IO 页面重命名与诊断化

调整方向：

- 菜单名从“Socket.IO 长链接”改为“Socket.IO 诊断”
- 页面说明改为“这是外部诊断入口，不是完整的内嵌后台”

页面行为：

- 显示当前建议连接地址
- 显示依赖条件说明
- 提供“打开外部诊断工具”按钮
- 如果当前环境不适合诊断，显示统一提示

预期收益：

- 从“伪功能页”改为“明确的诊断页”

### 6.5 统一错误文案工具

新增一个轻量错误格式化函数，例如：

- `formatAdminError(err, fallback)`

职责：

- 提取 axios / response / message / string 类型错误
- 转成管理员可理解的文本
- 尽可能避免直接出现 `[object Object]`

输出风格：

- 优先显示明确错误原因
- 如果是未配置/未接入，追加操作建议
- 如果拿不到具体原因，退回到页面级默认文案

第二轮覆盖范围：

- `ops-control`
- `defense-control`
- `plugin-permissions`
- `socketio`
- 资源页中最明显的自定义动作错误

### 6.6 资源页动作的最小加固

对以下位置做最小加固：

- 用户管理中的封禁/解封
- 群组管理中的添加成员

措施：

- 不改业务逻辑
- 只统一错误展示方式

目标：

- 避免资源页继续出现“失败了但提示极差”的问题

## 7. 菜单与命名调整

本轮菜单命名调整：

- `插件发布与权限` → `插件注册表`
- `Socket.IO 长链接` → `Socket.IO 诊断`

保留原分类：

- `插件注册表` 仍放在 `插件`
- `Socket.IO 诊断` 仍放在 `安全与防御`

原因：

- 本轮重点是降级和认知修正
- 不再一次性大调一级分类，避免改动过大

## 8. 测试策略

继续使用“先写失败用例，再改代码”。

新增回归测试至少覆盖：

1. 插件页已改名为“插件注册表”
2. Socket.IO 页已改名为“Socket.IO 诊断”
3. 插件页在注册表不可读时会进入统一降级态
4. Socket.IO 页具备诊断页文案，不再伪装成功能页
5. 错误格式化工具被关键页面接入

验证方式：

- `node --test server/admin/tests/...`
- `pnpm --filter tailchat-admin build:client`

## 9. 风险与控制

### 风险 1：文案变动导致认知切换成本

控制：

- 只改最误导的两个页面名
- 其它页面先不大动

### 风险 2：统一错误处理抽象过度

控制：

- 只做轻量函数和轻量卡片
- 不引入新的复杂状态管理

### 风险 3：前端页面改动后编译回归

控制：

- 保持第二轮仍以客户端构建通过为验收条件

## 10. 验收标准

当以下条件满足时，第二轮视为完成：

- 后台中不再出现“插件发布与权限”这个误导性名称
- 后台中不再出现“Socket.IO 长链接”这个误导性名称
- 插件页文件缺失时，用户看到明确降级提示，而不是空表格伪成功
- Socket.IO 页明确呈现为诊断入口
- 关键页面不再普遍直接 `Message.error(String(err))`
- 第二轮回归测试通过
- 管理端前端构建通过
